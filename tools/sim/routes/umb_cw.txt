# UMBmark square, clockwise (tools/sim/umb_suite.py). The robot's own routine drives the same square and prints
# the [UMB] line; a person measures where the robot really ended. Real minus believed is the odometry error.
# Frame: setPose(0, 0, 0), so x is to the robot's right at the start, y is forward, heading clockwise.
# Side 48 in (UMB_SIDE_IN). Every leg forwards with moveToPoint, every turn on the spot, both at maxSpeed 70 of 127
# (UMB_DRIVE_MAX_SPEED, UMB_TURN_MAX_SPEED). It stands still 2000 ms first (UMB_STILL_MS: the heading change over
# that time gives still_dps), stops 300 ms after every move (UMB_STOP_MS) and 1000 ms more after the last turn
# (UMB_SETTLE_MS) before the pose is read. Turns go the shorter way, as TeamChassis::turnToHeading does by
# default; every turn is 90 deg, so that is always clockwise here. Time limits as the routine's: 5000 ms a leg
# (UMB_DRIVE_TIMEOUT_MS), 3000 ms a turn (UMB_TURN_TIMEOUT_MS); the routine ends the run at the first one, this route
# carries on. umb_suite.py checks this file against the square it builds itself (square_route).
# The robot's tracking-wheel offsets are NOT in this file: umb_suite.py passes them (--set VERT_OFFSET=-0.6 --set
# HORIZ_OFFSET=-2.23 --odom-offsets -0.6:-2.23). Run bare with tb_live, it gets the bench's old 0.9 / 2.55.
# Also not here: the routine sets the pose twice, 20 ms apart (a route has one start), and it watches the sticks
# every 10 ms while LemLib runs each move in its own task, so each stop can be up to 10 ms longer.
start 0 0 0
wait 2000
point 0 48 max=70 timeout=5000
wait 300
turn 90 max=70 timeout=3000
wait 300
point 48 48 max=70 timeout=5000
wait 300
turn 180 max=70 timeout=3000
wait 300
point 48 0 max=70 timeout=5000
wait 300
turn 270 max=70 timeout=3000
wait 300
point 0 0 max=70 timeout=5000
wait 300
turn 0 max=70 timeout=3000
wait 300
wait 1000
